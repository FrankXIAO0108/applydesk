# MVP 验证记录

## v0.3：新用户与对话入口

- 在包含空格的全新 Windows 目录中，用 Codex 自带 Node 启动；目录内没有 node_modules、npm 或业务数据库。启动器下载并验证 npm、安装 338 个依赖包、执行全部迁移，成功返回健康实例。
- 原有端口占用时自动选择其他端口；重复启动返回同一实例，不要求用户杀掉其他服务。
- 新用户默认没有启用公司，也没有继承个人投递跟踪；城市在首次网页配置中由使用者填写。
- 验证对话式配置、自定义公司、指定公司手动重查、暂停自动任务不影响手动操作、数据写回和回读、未检查不能标成功。
- 用浏览器实际读取一个字节跳动公开职位详情，通过 CLI 导入隔离实例并回读。没有遍历公司职位库，因此记录为 partial，未宣称全站已完成。
- 检查下载内容被篡改时启动器拒绝使用。新旧 API 与类型检查通过；CI 增加 Windows/Linux 全新启动流程。
- macOS 启动脚本尚未做真机测试；未用新用户账号验证全部招聘网站。此版本仍依赖 Codex 和浏览器插件。

本次在 Windows / Node.js 24 的空项目导出上完成本地验证：

- 干净依赖安装、本地迁移、开发服务启动与页面实际加载。
- 12 个单元测试通过；覆盖地点与实习筛选、状态解释、日期精度、链接规范化和飞书请求错误处理。
- TypeScript 类型检查、生产构建、隐私标记扫描通过。
- 3 组串联 API 冒烟测试通过；覆盖重复导入、决策保留、确认不等于投递、失败保留原状态、事务回滚、公司域名/路径隔离和跨源拒绝。
- 本地虚构示例：北京岗位进入推荐，上海岗位被排除。

## 对抗式检查

1. 外部请求能否冒充本地用户？开发入口剥离传入身份头，同时校验 TCP 来源和 Host 为回环地址；生产 API 不使用开发身份。
2. 登录失败是否会覆盖岗位原状态？测试验证保留原状态和最近成功检查时间。
3. 是否把“确认要投”当作投递成功？测试验证确认不会设置实际投递时间。
4. API 测试是否会写入真实飞书？仅在未配置飞书时验证同步拒绝；不会执行已配置环境的外部同步。
5. 是否把计划能力包装为已实现？README 和路线图明确列出采集器、调度、简历匹配、自动提交及生产认证的缺口。

## 未验证项

- GitHub Actions 的运行结果需以仓库中的实际记录为准，本地通过不能替代远程 CI。
- 本导出未向真实公司提交申请，也未使用真实飞书凭据执行同步。飞书传输层使用模拟响应测试。
- 未做公网部署、多人并发和浏览器采集器验收。
